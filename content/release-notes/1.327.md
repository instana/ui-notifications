## Features

The following features are added in release 1.0.327:

### AI gateway: Capabilities tab

The AI gateway now includes a **Capabilities** tab that decouples capability management from AI connection configuration. You can assign AI connections to individual generative AI capabilities, and enable or disable each capability independently. Multiple capabilities can share the same AI connection, or each can use a different one.
Previously, enabling or disabling AI connections controlled access to generative AI features. You can now manage this directly for each capability from the Capabilities tab, without changing your AI connections.

For more information, see the following topics:
- [AI gateway](https://www.ibm.com/docs/en/instana-observability/saas?topic=instana-ai-gateway)
- [Managing capabilities](https://www.ibm.com/docs/en/instana-observability/saas?topic=gateway-managing-capabilities)
- [Managing AI connections](https://www.ibm.com/docs/en/instana-observability/saas?topic=gateway-managing-connections)

### BrowserScript recording with the IBM Instana Synthetic Test Recorder

Instana Synthetics now includes BrowserScript recording, a capability that streamlines the creation of synthetic browser tests. By using the IBM Instana Synthetic Test Recorder Chrome extension, you can record real browser interactions and automatically generate Playwright (an open-source browser automation framework) scripts for use as BrowserScript tests.
This recording experience reduces manual scripting effort, making it easier to create, customize, and maintain synthetic monitors for critical user journeys.

### Log perspectives

You can now create log perspectives to define filtered subsets of log data and enforce role-based access control on them. A log perspective acts as a scoped view of logs that you can assign to specific teams. Team members can view only the logs within the perspectives assigned to their team.

To get started, create a log perspective in **Logs** > **Log perspectives**, and then assign it to a team in **Settings** > **Security & Access** > **Teams**. For more information, see [Create a log perspective](https://www.ibm.com/docs/en/instana-observability/saas?topic=logging-role-based-access-control-rbac-logs#log-perspectives-public__create-a-log-perspective).

When you assign a team to a log perspective, Instana no longer applies the role-based access control previously enforced through application perspectives to that team. Configure your log perspectives correctly before you assign teams to avoid gaps in access control.
{: important}

For more information, see [Role-based access control (RBAC) for logs](https://www.ibm.com/docs/en/instana-observability/saas?topic=logging-role-based-access-control-rbac-logs).

### Mobile apps business impact

You can use the Business impact dashboard to see how releases and alerts affect the business metrics for your mobile application, such as active sessions, active users, and most-visited views. For more information, see [Business impact for mobile apps](https://www.ibm.com/docs/en/instana-observability/saas?topic=websites-business-impact).

### Monitoring IBM watsonx Orchestrate ADK

Instana now supports monitoring applications built with the IBM watsonx Orchestrate Agent Development Kit (ADK). Export telemetry from watsonx Orchestrate to Instana and view agent traces in the **Analytics** tab to gain visibility into agent execution and workflows.

For more information, see [Monitoring IBM watsonx Orchestrate ADK](https://www.ibm.com/docs/en/instana-observability/saas?topic=frameworks-ibm-watsonx-orchestrate-adk).

### Smart Alerts for Generative AI Observability

You can now create Smart Alerts from the Generative AI Observability page in the Instana UI. These alerts can be used to monitor generative AI services and LLM models to reveice notifications when metrics like token usage, costs, or request volumes exceed defined thresholds.

For more information about how to create a Smart Alert from the Generative AI Observability page, see [Smart Alerts for Generative AI Observability](https://www.ibm.com/docs/en/instana-observability/saas?topic=guides-smart-alerts-gen-ai-observability).

## Improvements

The following improvements are provided in release 1.0.327:

### Chrome upgrade for the Synthetic PoP BrowserScript engine

The Synthetic PoP BrowserScript playback engine is upgraded from Chrome 144 to Chrome 154. This upgrade resolves several high-severity common vulnerabilities and exposures (CVEs).
Chrome can deprecate features between major versions. Because of this version change, review the [Chrome release notes](https://developer.chrome.com/release-notes) for deprecated features that might affect your browser-based synthetic tests.

### Incorrect values in the Network Interfaces table

In the **Network Interfaces** table for Host, OTel Host, and Remote Host entities, Instana displayed throughput and rate values in incorrect units. Instana now displays these values correctly in bytes per second or operations per second, as appropriate.

### Kubernetes Cluster Name tag for OpenTelemetry calls

OpenTelemetry calls that are linked to a Kubernetes Pod infrastructure entity now include the **Kubernetes Cluster Name** tag.

### OpenTelemetry delta and cumulative sum metrics

Instana now correctly distinguishes between OpenTelemetry sum metrics that use **delta** temporality and those that use **cumulative** temporality. Previously, both were stored under the same metric path and processed identically, leading to incorrect aggregation results for delta counters.

Instana now routes each temporality to a dedicated metric path:

- Delta sums are stored under `metrics.sums_delta.*` and aggregated as zero-filled counts (the per-interval increment is used as-is).
- Cumulative sums are stored under `metrics.sums.*` (backwards-compatible) and `metrics.sums_cumulative.*`, and aggregated as a mean snapshot.

When both temporalities are reported for the same metric, the cumulative value takes precedence in the undifferentiated `metrics.sums.*` bucket.

Built-in dashboards for OpenTelemetry hosts and Kubernetes clusters are updated to reflect this change.

### Redesigned UI workflow for Smart Alerts for applications

The UI workflow for creating Smart Alerts for applications is updated to use a wider, step-by-step panel to guide you through creating an alert. This process guides you through selecting the alert condition blueprint, defining the alert scope, metric and threshold, and other configuration settings within a more streamlined workflow. For more information, see [Smart Alerts for applications](https://www.ibm.com/docs/en/instana-observability/saas?topic=applications-smart-alerts).

### Stack view

OpenTelemetry Kubernetes entities, previously listed under the **Infrastructure** section, are now grouped under the **Kubernetes** section.

### vLLM: New p99 rate metrics for queue time and request latency

Two New vLLM metrics are now collected and displayed in the **OTel vLLMonitor** dashboard:

- `vllm:request_queue_time_rate30m_p99` : The 99th percentile of queue wait time, calculated over a rolling 30-minute window.
- `vllm:request_latency_rate30m_p99` : The 99th percentile of end-to-end request latency, calculated over a rolling 30-minute window.

These metrics provide a high-percentile view of scheduling and serving latency without requiring manual histogram aggregation.

## Fixes

The following issues are fixed in release 1.0.327:

### Call counts in the Analytics Calls view

In the **Analytics** > **Calls** view, the call count displayed above the calls table did not include database calls that were [aggregated from multiple batched calls](https://www.ibm.com/docs/en/instana-observability/saas?topic=instana-analyzing-traces-calls#automatic-aggregation-of-short-exit-calls__title__1). As a result, database services could show lower call counts in this view than in dashboards. This issue is fixed, and call counts are now consistent across all views.

### Missing Kubecost metrics in filters and queries

When filtering or querying Kubecost entities, cluster-level metrics, such as cluster cost details and monthly savings, were not available as filter criteria. This issue is now fixed. Instana exposes these metrics correctly, and you can filter and query Kubecost entities by using their full set of metrics.

### OpenTelemetry Kubernetes nodes missing cluster association

Previously, when a new OpenTelemetry Kubernetes node joined an existing cluster, the node was not correctly associated with its cluster. As a result, the node was missing from topology views and returned incorrect results when filtered by cluster. This issue is now fixed.

### Readable message for WebGL2 error

A readable error message is now displayed when WebGL2 fails on 3D objects rendering.

### Service disruption caused by memory exhaustion on startup for large tenants

For tenants with a large number of monitored entities, Instana could fail to start because it ran out of memory while loading entity data. This caused a restart loop that prevented the service from recovering automatically. This issue is now fixed. Instana handles large entity sets on startup without exhausting memory, and recovers if memory is exhausted.

### Stale entity data for large tenants

For large tenants, the process responsible for removing outdated entity snapshots did not run reliably. As a result, stale entity data accumulated over time and caused incorrect information to appear for entities in Instana. This issue is now fixed, and Instana cleans up entity data correctly for all tenant sizes.

### Stale entities appearing in Analyze Infrastructure

In **Analyze Infrastructure**, entities that had expired could reappear and return incorrect results, including outdated tag values, for days after expiry. Now, expired entities are removed correctly and no longer appear in queries or analysis views.
