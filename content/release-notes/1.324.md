## Features

The following features are added in release 1.0.324:

### Scheduled LLM evaluations

You can now schedule LLM evaluations to run automatically on a daily or weekly cadence. When you create or edit an evaluation definition, use the **Schedule** dropdown to set the recurrence, configure a start date, and choose an end condition. Scheduled runs automatically select traces that match your filter criteria and apply the configured sampling percentage.

For more information, see [AI evaluation in Instana](https://www.ibm.com/docs/en/instana-observability/saas?topic=features-ai-evaluation-in-instana#scheduling_recurring_evaluations__title__1).

### Email payload transformation with JSONata

You can now use JSONata expressions to transform email alert payloads when you create email alert channels through the API. You can customize the content of email alerts, such as the subject line, severity label, and custom payload fields, to better suit your team's notification workflows.

For more information, see [Email payload transformation with JSONata](https://www.ibm.com/docs/en/instana-observability/saas?topic=alerting-email#payload_transformation__title__1).

### Burn rate window comparison for SLO dashboard

The SLO burn rate chart now supports overlaying multiple time windows simultaneously. In the chart header, click **Burn rate comparison** to select from recommended window pairs or define custom windows. For more information, see [Comparing burn rate windows](https://www.ibm.com/docs/en/instana-observability/saas?topic=slos-service-level-objectives#slo-details__burn-rate-window-comparison__title__1).

### Display name

You can now assign display names, such as UAT, Production, or Staging-US-East, to your tenant-units (TUs).

The display name is separate from the tenant unit's immutable URL. You can rename a tenant unit at any time to reflect organizational changes without affecting backend connections, data ingestion, or API endpoints. Display names help you identify tenant units in the product without referencing their URLs.

By default, Instana uses the tenant name from the URL as the display name.

For example:
- URL: `https://acme-prod.instana.io`
- Display name (default): `acme-prod`

## Improvements

The following improvements are provided in release 1.0.324:

### AWS metric streams: Support for AWS MSK and AWS Neptune

AWS metric streams now supports metrics from AWS Managed Streaming for Apache Kafka (AWS MSK) and AWS Neptune.

- AWS MSK: Instana can ingest metrics from the `AWS/Kafka` namespace. Cluster-level metrics use the `Cluster Name` dimension, while broker-level metrics use both the `Cluster Name` and `Broker ID` dimensions.
- AWS Neptune: Instana can ingest metrics from the `AWS/Neptune` namespace with the `DBClusterIdentifier` and `DBInstanceIdentifier` dimensions.

For more information, see [Supported AWS CloudWatch namespaces and dimensions](https://www.ibm.com/docs/en/instana-observability/saas?topic=integrations-aws-metric-streams-public-preview#GUID-e52ea023-542f-4e84-b4f2-610ecca4b1f7__Supported-AWS-CloudWatch-namespaces-and-dimensions__title__1).

### Gen AI observability: Support for Traceloop SDK version 0.62.3

Gen AI observability features, including the **Task hierarchy** view, **Trajectory** view, and **Traces** page, now support Traceloop SDK version 0.62.3. This version adds support for the following newly emitted attributes:

- `gen_ai.input.messages`: JSON array representing chat turns and user inputs.
- `gen_ai.output.messages`: JSON array representing model responses.
- `gen_ai.system_instructions`: JSON array that represents instructions for the system prompt, emitted separately from chat turns.

For more information, see [Get started with Gen AI Observability](https://www.ibm.com/docs/en/instana-observability/saas?topic=observability-getting-started).

### Role merging within Team Scope

Users assigned multiple roles within a team no longer experience unexpected loss of access to product areas within Team Scope. Previously, the system inadvertently blocked access to areas that at least one role was meant to allow when roles with different access restrictions were combined. Now, an area is only restricted if every assigned role restricts it. Users receive the broadest access their roles permit. The "Default Scope" behavior remains unchanged.
